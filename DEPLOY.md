# Deploying Flowline to ckltask.com

Everything in this document is a step a person has to take in a browser —
creating accounts, pasting secrets, pointing DNS. The repository is already
configured for all of it.

Work through the parts in order. Part 1 and Part 2 are independent, so the
database can be set up while DNS propagates.

---

## Part 1 — The database (Supabase, free tier)

Flowline stores everything in Postgres and relies on Row Level Security to
decide who can see what. The free tier is far more than a single company
needs; the limit that matters is 500 MB of storage, and a task is a few
hundred bytes.

### 1.1 Create the project

1. Sign up at <https://supabase.com> and create a new project.
2. Choose the region closest to your team — for India, **Mumbai
   (`ap-south-1`)**. This is the single biggest factor in how fast the app
   feels, and it cannot be changed later without recreating the project.
3. Set a strong database password and store it in a password manager. It is
   shown once.

### 1.2 Create the schema

For a **new, empty project** — which this is — paste one file:

1. Open `supabase/schema.sql` (78 KB, 1,883 lines).
2. Supabase dashboard → **SQL Editor** → **New query**.
3. Paste the whole file, **Run**.

That is the entire schema: tables, row level security, functions, triggers
and realtime.

`schema.sql` is generated by `npm run schema:build`, which concatenates
`supabase/migrations/*.sql` in filename order and nothing else. Applying it to
a fresh database is therefore identical to applying all eleven migrations in
sequence — with one paste instead of eleven, and no chance of running them out
of order.

Regenerate it whenever a migration is added:

```bash
npm run schema:build
```

**Run the numbered migrations individually only when upgrading a database that
already has data**, where you need to apply just the new ones. The order
matters there — later migrations depend on functions and tables the earlier
ones create:

```
0001_init.sql                        0007_sop_categories.sql
0002_helpers.sql                     0008_calls_rollover_periods.sql
0003_triggers.sql                    0009_org_timezone.sql
0004_rpc.sql                         0010_authorization_hardening.sql
0005_rls.sql                         0011_task_events_and_safeguards.sql
0006_realtime.sql
```

### 1.3 Create the first owner

Flowline never creates accounts by itself — signing in with an unknown email
is refused on purpose. The first account has to be made by hand:

1. **Authentication → Users → Add user**, using your real work email.
   Tick *Auto Confirm User*.
2. **SQL Editor**, substituting your email:

   ```sql
   insert into public.profiles (id, full_name, job_title, role)
   select id, 'Your Name', 'Owner', 'admin'
   from auth.users
   where email = 'you@yourcompany.com';
   ```

   `profiles` deliberately holds no email column — the address lives in
   `auth.users` and is joined when needed, so there is one copy of it and one
   place to change it.

3. Everyone else you add from inside the app, once you are signed in.

### 1.4 Point Supabase at the domain

**Authentication → URL Configuration**:

- **Site URL**: `https://ckltask.com`
- **Redirect URLs**: add `https://ckltask.com/auth/callback`

Sign-in links will not work until this is set — Supabase refuses to redirect
anywhere it has not been told about, which is the behaviour you want.

### 1.5 Collect the keys

**Project Settings → API**. You need three values:

| Value | Where it goes |
| --- | --- |
| Project URL | `NEXT_PUBLIC_SUPABASE_URL` |
| `anon` `public` key | `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| `service_role` `secret` key | `SUPABASE_SERVICE_ROLE_KEY` |

The first two are safe in a browser — Row Level Security is what protects the
data, not the secrecy of that key.

**The `service_role` key is different.** It bypasses Row Level Security
entirely. Anyone holding it can read and change every row belonging to every
user. It goes into Netlify's environment variables and nowhere else — never
into the repository, a screenshot, or a chat message. If it is ever exposed,
rotate it immediately from the same page.

## Part 2 — Hosting (Netlify, free tier)

Netlify's free tier permits commercial use, includes TLS certificates that
renew themselves, and runs Next.js server routes and middleware. Flowline
needs all three.

> Hostinger was the original plan and does not fit. Their shared hosting runs
> PHP and static files; Flowline needs a Node server for its middleware, its
> `/api/*` routes and the Supabase auth callback. Hostinger's Node offering is
> a paid VPS you would administer yourself — Node, a process manager, Nginx
> and certificate renewal. Netlify does that for nothing.

### 2.1 Connect the repository

1. Sign up at <https://netlify.com> with the GitHub account that owns
   `shlokjethwa14-collab/flowline`.
2. **Add new site → Import an existing project → GitHub**, and pick the
   repository.
3. Accept the detected settings. `netlify.toml` already specifies the build
   command, the publish directory and the Node version.
4. **Do not deploy yet** — add the environment variables first, or the first
   build produces a site running in demo mode.

### 2.2 Environment variables

**Site configuration → Environment variables**, adding each as *Same value
for all deploy contexts*:

| Key | Value |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | from 1.5 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | from 1.5 |
| `SUPABASE_SERVICE_ROLE_KEY` | from 1.5 — mark **Secret** |
| `NEXT_PUBLIC_SITE_URL` | `https://ckltask.com` |
| `ANTHROPIC_API_KEY` | optional, for call summaries — mark **Secret** |

Then trigger a deploy. It should finish in two or three minutes.

### 2.3 Add the domain — `ckltask.com` at GoDaddy

The domain is registered at GoDaddy and currently parked: its nameservers are
`ns01.domaincontrol.com` / `ns02.domaincontrol.com`, the apex points at
GoDaddy's parking addresses, and there are **no MX records**, so no email is
at risk in what follows.

There are two ways to connect it. They are not equivalent.

#### Option A — Netlify DNS (recommended here)

Hand GoDaddy's nameservers over to Netlify. Netlify then manages every record
for the domain.

Netlify recommends this for apex domains for a concrete reason: with external
DNS the apex can only be an `A` record pointing at a single load-balancer IP,
which cannot use their global CDN routing. GoDaddy does not support
`ALIAS`/`ANAME` records, so external DNS at the apex has no better option.

The usual argument against delegating — it moves your existing records, and
mail is the one that hurts — does not apply: there is nothing to move.

1. Netlify: **Domain management → Add a domain** → `ckltask.com` → **Add a
   domain you already own**.
2. Choose the Netlify DNS option. Netlify shows four nameservers in the form
   `dns1.p01.nsone.net`. **They are assigned per domain — use the four your
   dashboard shows, not any you find in a tutorial.**
3. GoDaddy: **My Products → ckltask.com → Domain Settings → Nameservers →
   Change → I'll use my own nameservers**. Replace both `domaincontrol.com`
   entries with Netlify's four. Save.
4. GoDaddy will warn that changing nameservers turns off its DNS. That is the
   intent; accept it.

Delegation typically completes within an hour, occasionally up to 48.

#### Option B — keep GoDaddy DNS

Use this if you later want GoDaddy managing mail or other records and prefer
one place for them.

GoDaddy: **My Products → ckltask.com → DNS → Manage Zones**.

**Delete first**, or the new records will fight the old ones and the site will
load intermittently:

- both `A` records on `@` (currently `76.223.105.230` and `13.248.243.5` —
  GoDaddy's parking addresses)
- the `CNAME` on `www` (currently pointing at `@`)

Then add:

| Type | Name | Value | TTL |
| --- | --- | --- | --- |
| `A` | `@` | `75.2.60.5` | 600 |
| `CNAME` | `www` | `<your-site>.netlify.app` | 600 |

A 600-second TTL rather than the hour GoDaddy defaults to: while you are
setting this up, a mistake should cost ten minutes to correct, not sixty. Put
it back to 3600 once the site is confirmed working.

Also check **Domain Settings → Forwarding** is empty. GoDaddy's domain
forwarding silently injects its own records and overrides the ones above —
it is the most common reason a correct-looking GoDaddy zone still serves a
parking page.

Confirm the `A` value against what Netlify's own panel shows you. `75.2.60.5`
is their documented load balancer, but their dashboard is the authority for
your site.

### 2.4 Set the primary domain

Back in **Domain management**, set `ckltask.com` as the primary domain so
`www` redirects to it rather than serving a second copy of the site at a
different address.

Netlify issues the TLS certificate automatically once DNS resolves. Until
then the site is reachable at its `.netlify.app` address.

## Part 3 — Checks before you tell anyone the address

Most of this is automated. From the repository:

```bash
npm run check:domain
```

It queries a public resolver rather than your machine's, because a local or
ISP resolver can hold a stale answer for hours — which during a domain move is
exactly the thing you are trying to see. It reports the nameservers, whether
the apex still points at GoDaddy's parking addresses, whether HTTPS is
enforced, whether every security header survived the trip through the host,
and — the one worth caring about most — whether `/my-day` is being served to a
signed-out visitor, which would mean the site is running in demo mode with no
database attached.

Run it after changing DNS, then again once the certificate appears. Expect
failures until both have happened.

Then do these by hand. Each has caught a real problem.

1. **`https://ckltask.com` loads the landing story** and the padlock is
   present.
2. **`http://ckltask.com` redirects to HTTPS**, and `www.ckltask.com`
   redirects to the bare domain.
3. **Sign in with your owner account.** The email arrives, the link works, and
   you land on Team Flow. If the link fails, 1.4 is wrong.
4. **Open a private window and visit `https://ckltask.com/my-day`.** You must
   be redirected to the sign-in page. If you see the app, stop and check the
   Supabase environment variables — the site is running in demo mode.
5. **Paste the link into WhatsApp.** The preview card should show the
   Flowline mark and the tagline.
6. **Run <https://securityheaders.com> against the domain.** Expect an A or
   A+. Anything lower means the middleware is not running.

## Part 4 — Running it properly

### Backups

Supabase's free tier keeps daily backups for seven days, which covers an
accident but not a bad month. Take your own copy periodically:

```bash
npx supabase db dump --db-url "postgresql://postgres:PASSWORD@db.PROJECT.supabase.co:5432/postgres" -f backup.sql
```

Keep it somewhere that is not the same laptop as everything else.

### Secret rotation

Rotate the `service_role` key at once if it is ever pasted anywhere it should
not be. Supabase Settings → API → *Generate new key*, then update the Netlify
variable and redeploy. The site is briefly broken between those two steps, so
do it deliberately rather than in a hurry.

### Cost

Everything above is free at this scale, and the free tiers are not trials.
The two figures worth knowing:

- Supabase pauses a project after **seven days with no requests**. A team
  using it daily will never see this; a project left idle over a long holiday
  will need un-pausing from the dashboard.
- Netlify's free bandwidth is 100 GB a month. Flowline's heaviest page is the
  landing story at roughly 400 KB, so that is about a quarter of a million
  visits.

### What is deliberately not automated

There is no CI pipeline running the test suite before deploy. The 50 tests
need a live Postgres on port 5433, which a Netlify build container does not
have. Run them locally before pushing to `main`:

```bash
npm run test:unit && npm run test:db
```

Adding a GitHub Actions workflow with a Postgres service container would close
this, and is the obvious next improvement.
